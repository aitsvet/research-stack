# Open WebUI + Qwen

Агент на моделях Qwen (DashScope / Alibaba Model Studio) внутри Open WebUI —
сервиса `open-webui` из корневого compose стека `zotero-setup`. Здесь лежит то,
что делает из него агента: сам пайп, установщик и пример прокси. Синхронизация
библиотеки Zotero между серверами — отдельная, независимая от OWUI подсистема:
SETUP.md, «Library sync between peers».

## Что в папке

| Файл | Назначение |
|---|---|
| `functions/qwen_auto.py` | Пайп-агент: один чат, три роли (текст/зрение/картинки) плюс поиск |
| `install_function.sh` | Идемпотентная установка пайпа через REST API (файл в контейнер не подложить) |
| `nginx.example.conf` | Прокси: `client_max_body_size 50m` + `proxy_buffering off` |

Сам контейнер OWUI описан **в корневом `docker-compose.yml`** рядом с zotero,
searxng и mcpo — отдельного compose здесь нет. Он тут был, дублировал корневой
и не запускался: `container_name` у обоих одинаковый, так что живым всё равно
оставался один. Переменные — в корневом `.env`.

## Развёртывание

```bash
cd ~ && git clone <репозиторий> zotero-setup && cd zotero-setup
cp .env.example .env && $EDITOR .env   # ZOTERO_*, DASHSCOPE_API_KEY, WEBUI_SECRET_KEY
docker compose up -d                   # zotero, open-webui, searxng, mcpo
./open-webui/install_function.sh       # ставит пайп, печатает список моделей
```

Установщику нужна учётка администратора OWUI — он берёт её из `open-webui/.env`
(`OWUI_URL`, `OWUI_EMAIL`, `OWUI_PASSWORD`); на пустом инстансе первый signup
и становится администратором. Больше этому файлу знать нечего: ключи и модели
живут в корневом `.env`.

**Установщик обновляет только код пайпа.** Значения валв Open WebUI хранит у
себя в базе, и уже установленному пайпу они достаются оттуда, а не из
окружения контейнера: переменные в compose — это умолчания для первой
установки. Меняете модель или ключ на работающем инстансе — правьте валвы в
интерфейсе (Admin → Functions → Qwen Auto → Valves), иначе правка compose
молча ни на что не повлияет.

Если библиотека должна приехать с другого сервера — сначала первичный перенос
синхронизацией (до `docker compose up`), см. SETUP.md.

Прокси: скопировать `nginx.example.conf`, подставить `server_name`/HTTPS,
`nginx -t && systemctl reload nginx`. Строка `client_max_body_size 50m`
обязательна: дефолтный лимит 1 МБ режет загрузку картинок 413-й ошибкой
(HTML вместо JSON), и фронтенд падает на `JSON.parse`.

Проверка: залогиниться, выбрать **Qwen Auto**, отправить текст, загрузить
картинку, попросить нарисовать и потом «поменяй фон».

## Пайп qwen_auto

Одна запись в селекторе, внутри детерминированная развилка + инструменты:
текст → `TEXT_MODEL`; картинка во вложении → `VISION_MODEL`; «нарисуй …» →
tool-call → `IMAGE_MODEL`; «поменяй фон/цвет …» → `IMAGE_EDIT_MODEL` (находит
исходник в чате).

| роль | модель | почему она |
|---|---|---|
| текст | `qwen3.8-max-preview` | сильнейшая в каталоге, вызовы инструментов держит |
| зрение | `qwen3.8-max-preview` | переписывает фото **дословно** (проверено) |
| рисование | `wan2.7-image` | 19 с на 1328×1328; `-pro` те же 1328 за 26 с |
| правка | `wan2.7-image` | та же модель принимает «картинка + указание» |

Отдельной зрительной модели в каталоге нет вовсе, и это не беда: зрение
встроено в основные. А вот дешёвая замена — беда: `qwen3.6-flash` на
проверочной картинке превратил «закят» в «закат», сохранив всё остальное. Для
расшифровки доски такая подмена хуже явной ошибки, поэтому зрение на 3.8.
Единственная текстовая модель без зрения — `qwen3.7-max`, она отвечает на
картинку `invalid_parameter`.

Вбитые в код факты: image-модели живут **только** на нативном эндпоинте
`/api/v1/services/aigc/multimodal-generation/generation` (в compatible-mode —
пустой `content`); размер холста задаётся только при рисовании, у правки его
диктует исходник; результат кладётся в файловое хранилище OWUI, в чат идёт
короткая ссылка `/api/v1/files/{id}/content`, а не мегабайтный data-URI; ответ
отдаётся асинхронным генератором (стриминг).

## Веб-поиск

Своими инструментами пайпа: `search_web` идёт в **SearXNG** (сервис в корневом
compose, `127.0.0.1:9090`), `fetch_url` дочитывает страницу. Модель сама решает,
когда их звать, — поэтому поиск не зависит ни от модели, ни от провайдера.

Родного поиска Alibaba (`enable_search`) на эндпоинте токен-пакета нет:
проверено — флаг принимается молча, поисковых полей в ответе не появляется, и
модель прямо отвечает, что доступа к интернету у неё нет. Валв `ENABLE_SEARCH`
в пайпе к тому времени уже никуда не был подключён — объявлен и не прочитан ни
разу; убран, чтобы не выглядел работающим.

Параллельно включён встроенный веб-поиск OWUI на том же SearXNG
(`ENABLE_WEB_SEARCH`): он подмешивает результаты в контекст до пайпа, кнопкой
в интерфейсе.

## Zotero MCP

MCP — плагин **внутри** контейнера zotero: `http://127.0.0.1:23120/mcp`
(streamable HTTP), `Authorization: Bearer $ZOTERO_MCP_TOKEN`. Плагин и токен
живут в профиле Zotero (`prefs.js` → `mcp.server.authToken`, там же
`requireAuth=true`, `allowRemote=true`).

Open WebUI 0.6.31+ подключает MCP нативно: **Admin → Settings → External Tools
→ Add → Type: MCP (Streamable HTTP)**, URL выше, Auth = Bearer с токеном. OWUI
в host-сети, так что `127.0.0.1:23120` доступен напрямую. Если сборка отвечает
`400 Bad Request` (open-webui#20500) — поставить рядом mcpo (MCP→OpenAPI
прокси) отдельным сервисом compose и подключить как OpenAPI-tool-server.

После подключения включить инструменты Zotero в настройках модели/чата —
агенты смогут и читать, и писать (`add_note`, `create_item`, `add_tags`,
коллекции, вложения).

## Источники для агентов

Всё через Zotero: источники и заметки кладёт в библиотеку штатный пайплайн
(`discover.py`, `ingest_sources.py`), агенты читают и пишут через Zotero MCP;
при нескольких серверах библиотеки сводит синхронизация (SETUP.md). Клоны
рабочих репозиториев не нужны; запасной вариант, если понадобится доступ к
сырым файлам, — mcpo + filesystem-MCP с репозиториями read-only в контейнере.
