# Корпус: зеркало Zotero и извлечение текста

Корпус (`$CORPUS`, отдельный приватный репозиторий-архив) — **зеркало
библиотеки Zotero в виде, удобном для LLM**: те же источники, но полным
текстом в markdown, разложенные по темам, с README в каждой папке. Zotero
остаётся авторитетной копией: метаданные, PDF, коллекции. Корпус нужен, чтобы
по источникам можно было искать `grep`, читать окнами и цитировать по
страницам, не поднимая Zotero и не передавая его целиком.

## Зеркало

- У каждого источника в корпусе есть запись в Zotero. В поле `extra` записи
  лежит путь к файлу в корпусе (`Локально: <корпус>/<путь>`). Имена файлов
  корпуса, полученных из Zotero, начинаются с ключа записи (`KEY_…` или
  `text/KEY.txt`).
- Расхождение в любую сторону — дефект, и о нём сообщают сразу, а не
  копят: файл без записи, запись с путём на отсутствующий файл, запись в
  коллекции без текста в корпусе.
- Проверка — `scripts/mirror_audit.py $CORPUS`. Она читает базу Zotero
  только на чтение и печатает расхождения по категориям. Прогонять после
  каждой загрузки и перед коммитом корпуса.
- Переименовал папку в корпусе — обнови пути в `extra` и в заметках Zotero.
  Сверять SQL-запросом с `instr()`, а не `LIKE`: в `LIKE` подчёркивание —
  шаблон, и `a_b` совпадает с `a-b`.

## Журнал добычи

Откуда и когда получен каждый источник, записано в одном файле в корне
корпуса — `acquisition_log.json`, по записи на источник. Ключ записи — ключ
Zotero, а если его нет — путь в корпусе. Поля: `path`, `zotero`, `title`,
`source` (откуда скачан), `page`/`doi`/`arxiv`, `published`, `retrieved`
(дата), `method` (`direct`, `oa`, `doi`, `arxiv`), `outcome` и `attempts`
(попытки с адресами и исходом), `extractor`, `pages`, `chars`, `complete`,
`flags`, `stored` (файл в `storage/` Zotero).

Скрипты дописывают его сами, если задана переменная
`ACQUISITION_LOG=<корпус>/acquisition_log.json`: `acquire.py`,
`retry_unpaywall.py`, `extract_texts.py` (оба режима), `chandra_ocr.py`,
`ingest_sources.py`, `discover.py --dois`.
Помощник — `scripts/acqlog.py`. Рабочие файлы прогонов (логи добычи и
повторов, манифесты текстов) остаются в каталоге `DISCOVERY_OUT` и в корпус
не копируются: всё, что в них есть о происхождении источника, уже лежит в
журнале. Материал, добытый руками, записывается в журнал тем же
`acqlog.record(...)`.

## Что версионируется

В git корпуса идёт **только текст**. Сами документы (`pdf`, `rtf`, `doc`,
`docx`, `odt`, `fb2`, `djvu`, `epub`, картинки, xlsx/zip-части дистрибутивов)
лежат рядом на диске и закрыты `.gitignore`: из истории они не
восстанавливаются, их резервная копия — забота владельца машины.

Полное извлечение каждого источника — `<имя>.md` рядом с ним, в общем
постраничном формате: метка `{N}` и строка из 48 дефисов перед каждой
страницей. В закоммиченных файлах не должно быть абсолютных путей хоста:
скрипты пишут пути относительно `storage/` Zotero или от `~`.

## Очередь

Что ещё не извлечено, всегда считается из файлов, а не берётся из списка.
Маршрут выбирается по наличию текстового слоя, а не по расширению: сканы и
цифровые PDF лежат вперемешку.

```bash
cd "$CORPUS"
find . -path ./.git -prune -o -type f \
     \( -iname '*.pdf' -o -iname '*.rtf' -o -iname '*.doc' \
        -o -iname '*.docx' -o -iname '*.odt' -o -iname '*.fb2' \) -print |
while read -r p; do
  [ -f "${p%.*}.md" ] && continue
  case "$p" in
    *.pdf|*.PDF) [ "$(pdftotext -l 3 "$p" - 2>/dev/null | tr -d '[:space:]' | wc -c)" -gt 300 ] \
                   && echo "TEXT   $p" || echo "OCR    $p" ;;
    *)           echo "OFFICE $p" ;;
  esac
done
```

## Чем извлекать

**TEXT — PDF с текстовым слоем.** Без OCR и GPU, принимает файлы и каталоги:

```bash
.venv/bin/python scripts/extract_texts.py md <файл-или-каталог> --suffix .md
```

**OCR — сканы.** Chandra на OpenAI-совместимом эндпойнте. Сервер vLLM слушает
петлю IPv6, а `getaddrinfo` в Python отдаёт только `127.0.0.1`, поэтому адрес
задаётся явно. Иначе запрос уходит в другой сервис на том же порту и
возвращается загадочный 404:

```bash
CHANDRA_URL='http://[::1]:8000/v1' \
  .venv/bin/python scripts/chandra_ocr.py "<файл>.pdf" --out "<файл>.md"
```

Порядок — от коротких документов к длинным: качество распознавания видно уже
на одной странице, а многостраничный скан идёт около минуты на страницу и
надолго занимает GPU.

**OFFICE — `.rtf/.doc/.docx/.odt`.** Через LibreOffice в контейнере `docconv`
(на хосте LibreOffice сознательно не ставится). Экспорт идёт через HTML,
поэтому таблицы переживают конвертацию:

```bash
CORPUS=<каталог> docker compose --profile tools run --rm docconv /corpus/<подкаталог> --dry-run
CORPUS=<каталог> docker compose --profile tools run --rm docconv /corpus/<подкаталог>
```

## Арабский текст

Текстовый слой арабских PDF, сделанных из Word, обычно даёт верные буквы, но
переставляет лигатуру лам-алиф: `لا` → `ال`, `لأ` → `أل`, `لإ` → `إل`.
Однозначно исправим только артикль перед хамзой в начале слова
(`اإل/األ/اآل` → `الإ/الأ/الآ`). Внутри слова перестановку не отличить от
настоящего `ال` (`أعمال`), поэтому остальное оставляют и цитируют по PDF.
PyMuPDF на таких файлах ломает ещё и порядок слов, так что лучший источник —
`pdftotext`. Chandra лигатуры восстанавливает, но подменяет похожие по
начертанию слова целиком, и такая ошибка меняет смысл. Поэтому для арабского
его берут только там, где текстового слоя нет.

## Проверка

Постраничный формат даёт дешёвый контроль полноты: меток `{N}` в `.md` должно
быть не меньше, чем страниц в PDF. Больше — нормально: `extract_texts.py`
режет альбомные страницы пополам. Меньше — часть страниц потерялась молча.
Отдельно искать `OCR FAILED`: так `chandra_ocr.py` помечает страницу, которую
эндпойнт не осилил даже после уменьшения картинки.

```bash
cd "$CORPUS"
find . -path ./.git -prune -o -type f -iname '*.pdf' -print | while read -r p; do
  m="${p%.pdf}.md"; [ -f "$m" ] || continue
  pages=$(pdfinfo "$p" 2>/dev/null | awk '/^Pages:/{print $2}')
  marks=$(grep -cE '^\{[0-9]+\}-{48}$' "$m")
  bad=$(grep -c 'OCR FAILED' "$m")
  { [ "$marks" -ge "$pages" ] && [ "$bad" = 0 ]; } || echo "BAD pdf=$pages md=$marks failed=$bad  $p"
done
```

Исключения, которые проверка показывает всегда, описываются в README папки,
где они лежат. Типичные:

- извлечение сделано до перехода на постраничный формат, и меток в нём нет;
- снимок веб-страницы: PDF отрисован браузером с навигацией и колонтитулами, а
  `.md` содержит очищенный текст, поэтому он по делу короче;
- книга, у которой страница PDF не равна странице книги (разворот по две
  страницы на лист, перевёрстка полосами). Там метки — книжные страницы, по ним
  цитируют и сверяют издания. Полнота проверяется сплошной нумерацией меток и
  сверкой с другим изданием.

У office-документов постраничной метки нет. Там сравнивается объём с
исходником, и глазами проверяется самый короткий результат в партии: пустая
или обрезанная конвертация выглядит как подозрительно маленький `.md`.
